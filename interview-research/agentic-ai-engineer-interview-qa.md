**1. 备考题库反复出现的方向（多个来源一致）**
- 什么时候用多智能体（multi-agent），什么时候单智能体就够了。常见的判断标准：单个智能体能不能完成、协调成本值不值得；子任务可以并行，或者需要独立的审核者时，才考虑多智能体。

## A. 智能体架构与编排（Agentic Architecture & LLM Orchestration）

### A1. 什么是智能体（agent）？它和普通的 LLM 工作流（workflow）有什么区别？
Anthropic 的"Building effective agents"一文给出的划分比较实用：**工作流**是由预先写好的代码路径来编排 LLM 和工具，流程是确定的；**智能体**是由 LLM 动态决定自己的流程和工具使用，在循环中根据环境反馈（工具结果）持续决策，直到完成或达到上限。判断标准是"控制流由谁决定"。工作流更可预测、便宜、容易测；智能体灵活，但成本、延迟和不确定性都更高。

### A2. 什么时候该用智能体，什么时候不该？
先问：任务的步骤是否事先能写出来？如果能，用工作流甚至普通代码。只有在步骤数和路径无法预先确定、错误成本可接受或可被验证、值得为灵活性付出成本时，才用智能体。不该用的信号：对延迟或成本极敏感、强合规要求每步可预测、一次调用就能解决、没有办法验证结果。实践上先从单次调用加检索开始，逐步增加复杂度，每增加一层都要用评测证明有收益。

### A3. 常见的编排模式有哪些？
Anthropic 总结的几种：提示链（prompt chaining，顺序拆分步骤并在中间加校验）、路由（routing，把输入分流给专门的处理）、并行化（parallelization，分段并行或多次投票）、编排者—工作者（orchestrator-workers，由主智能体动态拆分子任务）、评估者—优化者（evaluator-optimizer，一个生成一个评审循环改进）。再复杂的就是自主智能体循环。面试时要能说出每种模式适用的场景和代价。

### A4. 规划（Planning）有哪些方式？怎么选？
几种常见做法：ReAct（边想边做，每步根据观察决定下一步，适应性强但容易发散）、先规划后执行（plan-and-execute，先产出完整计划再执行，可对计划做校验和审批，遇到偏差需要重规划）、分层规划（上层目标分解成子目标）、带反思的循环（reflection，对结果自我评价后改进）、搜索类方法（对多个候选计划打分选择，成本高）。选择取决于任务的可预测性、需要的可审计性和成本。要提到：把计划表示为结构化数据（比如带依赖的有向无环图），执行前做校验，是提高可控性的好办法。

### A5. 什么是上下文工程（context engineering）？
指在智能体运行的每一步，精心管理放进上下文窗口的内容，而不只是写好一段提示词。包括：系统提示和工具描述的设计、检索进来的资料、历史消息的压缩与摘要、工具结果的清理、把子任务交给子智能体以隔离上下文、结构化笔记（把关键信息写到外部再按需读回）。目标是让每一步的上下文既足够又精简，因为上下文越长，成本越高，模型注意力也越容易分散。

### A6. 多智能体系统什么时候比单智能体好？有什么代价？
适合：子任务可以并行（比如多路调研）、需要不同的工具集或权限隔离、需要独立的审核者来降低盲区、单个上下文放不下。代价：协调开销、token 成本成倍增加（Anthropic 公开的多智能体研究系统文章里提到过，多智能体比普通聊天多消耗十几倍的 token，具体数字请自己核对）、调试更难、错误会在智能体之间传播。原则是先证明单智能体不够，再拆分；并且要有明确的交接协议和共享状态设计。

### A7. 多智能体有哪些常见拓扑？
监督者（supervisor/router）模式：一个主智能体分派给专职智能体；层级式：多层监督；交接（handoff/swarm）：智能体之间移交控制权，由当前智能体决定下一位；黑板（blackboard）：智能体读写共享状态；辩论或投票：多个智能体独立回答再汇总。选择时看：谁拥有全局状态、谁决定终止、失败时由谁兜底、通信的数据量。

### A8. LangGraph 的核心概念是什么？
LangGraph 把智能体建模成有状态的图：**状态（State）**是一个带类型的共享结构，每个字段可以配 reducer 决定并发更新如何合并；**节点（node）**是读状态、返回更新的函数；**边（edge）**决定流向，可以是条件边（根据状态路由）；支持循环；**检查点（checkpointer）**在每一步把状态持久化，以 thread 为单位，支持暂停、恢复、回放和"时间旅行"；支持人工介入的中断与恢复、子图、并行扇出。它的强项是对控制流和状态的显式、细粒度控制，适合长流程和需要可恢复的场景。

### A9. LangGraph、CrewAI、AutoGen、Semantic Kernel、OpenAI Agents SDK 怎么对比？
这是常见的开放题，建议按"控制流模型、状态管理、持久化、可观测、生态与维护状态"来答。大致印象（请以最新文档为准）：LangGraph 是显式图加检查点，控制力最强；CrewAI 以角色和任务为中心，上手快，也有 Flow 管理状态，偏流水线式；AutoGen 以多智能体对话为核心，据报道已转入维护模式，新项目被引导到 Microsoft Agent Framework；Semantic Kernel 偏企业开发，C# 和 Python 支持较好，有插件概念，也在与微软的新框架融合；OpenAI Agents SDK 提供轻量原语（智能体、工具、交接、护栏、追踪）。回答的关键是说明你为什么在某个场景选某个框架，以及什么时候不用框架、直接写循环。

### A10. 为什么有些团队不用框架，直接自己写智能体循环？
框架抽象可能隐藏提示词、增加调试难度、版本变动大、与自家基础设施（持久化、鉴权、可观测）不合。智能体的核心循环其实很简单：调用模型、解析工具调用、执行、把结果追加回消息、判断是否结束。自己写能完全掌控重试、预算、权限和日志。但自己写要承担状态持久化、恢复、并发等重复工作。折中：用框架做原型，生产中只保留需要的部分，或者把持久化交给专门的工作流引擎。

### A11. 一个智能体循环的最小实现是什么样？
```python
def run(task, tools, max_steps=20, budget_tokens=200_000):
    messages = [system_prompt, user(task)]
    for step in range(max_steps):
        resp = llm(messages, tools=tools)
        messages.append(resp.message)
        if not resp.tool_calls:
            return resp.text                      # 终止条件：模型不再调用工具
        for call in resp.tool_calls:
            result = execute_with_guardrails(call)   # 校验、权限、超时、幂等
            messages.append(tool_result(call.id, result))
        if tokens_used(messages) > budget_tokens:
            raise BudgetExceeded()
    raise MaxStepsExceeded()
```
面试加分点：步数与预算上限、并行工具调用、工具错误作为结果返回给模型而不是抛异常、每一步落盘（可恢复）、循环检测。

### A12. 怎么检测并终止智能体的无限循环或重复调用？
几种互补的手段：硬性上限（步数、墙钟时间、token 与费用）；对"工具名加规范化后的参数"计数哈希，重复超过阈值就中断或注入提示让模型换策略；检测状态无进展（连续几步状态摘要不变）；任务完成判据显式化（由校验器判断，而不是让模型自己说"完成了"）；超限后降级为人工介入，并保留完整追踪。还要在提示词和工具返回里明确告知"失败时该怎么做"，而不是让模型盲目重试。

### A13. 什么是状态机（state machine）式的智能体设计？为什么有用？
把智能体流程显式建模为有限状态机：有明确的状态、转移条件（guards）、超时、终止状态，LLM 只是决策或生成内容的一个组件，而不是隐含地掌管整个流程。好处：流程可审计、可测试、可持久化、可恢复；非法转移可以被拒绝；容易加人工审批点。实现上状态要序列化存储，转移要幂等，转移事件要记录。这也是长时间运行智能体的基础。

### A14. 智能体的记忆（memory）怎么分类和设计？
常见分法：短期记忆（当前会话或线程的状态与消息历史）、长期记忆（跨会话保存的用户偏好、事实、过往经验）。长期记忆又可分为语义（事实）、情景（过去的事件和轨迹）、程序性（学到的做法或指令）。设计要点：什么时候写入（每轮、按规则、由智能体显式调用）；怎么存（键值、向量检索、图）；怎么读回（检索排序、相关度阈值）；怎么更新和遗忘（去重、过期、冲突解决）；隐私与删除（合规）；按租户和用户隔离。风险：错误的记忆会被反复引用，需要来源和置信度。

### A15. 长对话或长任务中，怎么管理上下文窗口？
手段：滑动窗口保留最近内容；对旧内容做摘要（压缩，compaction），并保留关键事实和未决事项；清理已经不需要的大块工具结果；把大对象放到外部存储，上下文里只留引用；用检索按需取回；把子任务交给子智能体，只返回精炼结果；利用提示缓存（prompt caching）降低固定前缀的成本。要说明摘要会丢信息，所以对关键事实用结构化字段存放，而不是只靠自然语言摘要。

### A16. 状态管理（State Management）：智能体的状态应该放在哪里？
把状态分层：①进程内的临时状态，丢了可以重建；②每一步都持久化的运行状态（消息、已完成步骤、待办、工具调用的意图与结果），放在持久存储（如 Postgres），以运行编号为键；③大对象和产物放对象存储，状态里只存引用；④需要共享或加速的缓存放 Redis 之类，但不能是唯一副本。编排器本身保持无状态，任何实例都能加载状态并从最后一个完成的步骤继续。要强调：状态模式（schema）需要版本化，因为长时间运行的任务可能跨越代码升级。

### A17. 长周期（long-running）智能体有哪些特殊问题？
运行时间从几分钟到数天；会遇到进程崩溃、部署重启、模型和工具超时、人工审批等待、外部事件触发。需要：持久化执行（durable execution）、可恢复的检查点、定时器和事件唤醒、版本管理（运行中的任务该用哪版提示词和代码）、预算和超时、可取消、可观察。不能用"一个进程里的 while 循环加内存状态"来做。

### A18. 人工参与（human-in-the-loop）怎么设计？
典型流程：智能体在某个动作前暂停，生成待审批请求（包含动作、参数、理由和风险），持久化后释放计算资源；审批人通过界面批准、修改或拒绝；系统收到信号后恢复。要考虑：审批超时与升级、审批期间上下文是否变化（需要重新校验）、批准内容的签名或版本（防止篡改）、审计日志、批量审批与自动化分级（低风险自动、高风险必审）。实现上依赖持久化状态加可靠的恢复机制，而不是占着一个进程等着。

### A19. Model Context Protocol（MCP）是什么？在智能体系统里怎么用？
MCP 是一个开放协议，让 LLM 应用以统一方式连接外部工具和数据：服务器暴露工具（tools）、资源（resources）、提示模板（prompts），客户端发现并调用，传输方式有本地进程的标准输入输出和基于 HTTP 的流式传输。优点：工具生态可复用、与具体模型和框架解耦。工程上要关注：服务器的信任与版本固定、工具描述被投毒或更换（"rug pull"）、认证与授权（代表用户的权限范围）、超时与错误语义、速率限制。企业场景通常要自建网关来集中管控和审计 MCP 服务器。

### A20. 智能体之间如何通信？提到 A2A 协议你怎么理解？
智能体间通信可以走共享状态（黑板）、消息队列、函数调用（把另一个智能体当工具）、或标准协议。A2A（Agent2Agent）是 Google 提出的、面向不同厂商智能体互操作的协议，关注能力发现、任务委托与状态同步；与 MCP 的定位不同，MCP 偏"智能体连接工具和数据"，A2A 偏"智能体连接智能体"。面试中要能说出：跨信任边界通信时需要认证、授权范围收窄（避免权限在委托链中悄悄扩大）、任务的可追踪与超时。协议细节请以最新规范为准。

### A21. 如何设计工具的接口，让模型用得更可靠？
Anthropic 的相关经验：工具名和描述要像给新同事写文档一样清晰；参数命名明确，减少歧义；返回信息精炼且对模型友好（避免返回海量原始数据，提供分页和过滤）；错误信息要可操作（告诉模型怎么修正）；合并相关的小工具为更高层的工具，减少调用次数；用评测来迭代工具的设计，看模型的实际调用轨迹。还要考虑让危险操作显式化（单独的工具、需要确认参数），而不是一个万能的"执行"工具。

### A22. 什么时候用结构化输出（structured outputs）和约束解码？
需要机器可读且必须符合模式时（工具参数、分类结果、计划）。可以用 JSON Schema 约束，供应商提供的结构化输出可以保证格式合法，但不保证内容正确，所以仍要做业务校验。对于推理类任务，过早强制结构可能影响质量，可以先让模型自由推理再输出结构化结果。校验失败时的修复循环要有次数上限。

### A23. 怎么选择模型？怎么做模型路由（model routing）？
按任务难度、延迟、成本、上下文长度、工具调用能力、数据合规来选择。路由策略：简单分类和提取用小模型，复杂规划用大模型；先用小模型尝试，置信度低或校验失败再升级；对不同步骤配置不同模型；保留多供应商的降级路径。必须用评测数据支撑选择，并持续回归，因为模型版本更新会改变行为。要固定模型版本号并管理升级流程。

### A24. 提示词和模型的版本管理应该怎么做？
把提示词、工具描述、模型版本、检索配置当作代码一样版本化、评审、灰度发布和可回滚；每个运行记录用的是哪个版本；变更必须过评测门槛（回归集）；运行中的长任务要固定使用启动时的版本，或有明确的迁移策略。供应商更换或更新模型时，要在影子流量（shadow）或灰度上比较。

### A25. 并行和流式在智能体里怎么用？
并行：模型一次返回多个互不依赖的工具调用时并发执行，降低延迟，要有并发上限和超时，以及部分失败的处理；对有依赖的调用要保序。流式：把模型的 token 和中间步骤的进展实时推给用户，改善感知延迟；需要处理取消（用户中断时要停止下游调用并回收资源）、流中断后的恢复、中间结果与最终结果的一致性。

## B. 工具调用、护栏与自纠错

### B1. 工具调用（tool calling / function calling）的完整流程是什么？
应用把工具的名称、描述和参数模式（JSON Schema）连同消息发给模型；模型决定是否调用以及参数，返回结构化的调用请求；**应用代码**（不是模型）校验并执行，把结果作为工具结果消息追加回去；模型据此继续或给出最终回答。关键认识：模型只是"提出"调用，执行权和责任在你的运行时，所以所有安全控制都应该放在执行层，而不是依赖模型自觉。

### B2. 把 LLM 安全地接入企业的 API、数据库和内部工具，设计原则有哪些？
最小权限（工具只暴露必要能力，数据库用只读账号或限定视图）；权限继承自终端用户（以用户身份调用，而不是用一个万能服务账号，避免"混淆代理"问题）；参数校验和白名单（对 SQL、路径、URL 严格限制）；速率与配额；敏感操作需要审批；凭证不进入提示词或模型可见的上下文，由运行时注入；完整的审计日志；超时、熔断和降级。对数据库，更推荐暴露参数化的、受限的查询工具，而不是让模型写任意 SQL。

### B3. 怎么设计高可靠的工具调用护栏（guardrails）？
分层设计：**输入侧**（对用户输入和检索内容做注入与敏感信息检测）；**调用前**（参数模式校验、权限检查、风险分级、预算检查、重复调用检测、需要审批的拦截）；**执行中**（沙箱、超时、资源限制、出口控制）；**输出侧**（结果脱敏、大小截断、对返回内容标记为不可信）；**调用后**（验证结果是否符合预期、写审计日志）。关键是把强制性规则放在代码和策略引擎里，让它们独立于模型的决策。

### B4. 如何处理工具返回的格式错误或异常输出？
分情况：瞬时错误（网络、限流）按退避重试；确定性错误（参数非法）把清晰的错误信息返回给模型让它修正，并限制修正次数；工具返回结构不符合预期（模式校验失败）视为工具故障，不把脏数据直接喂给模型；超大输出截断并提示如何分页；多次失败后升级（换策略、转人工、终止）。所有失败都要记入追踪，便于事后分析。

### B5. 如何保证工具调用的幂等性（idempotency）？
给每次有副作用的调用生成稳定的幂等键（例如由运行编号、步骤编号、业务意图派生，而不是每次重试都变），下游系统用它去重；运行时在执行前先记录"意图"，执行后记录"结果"，崩溃恢复时先查询下游或本地记录，决定是跳过、补记还是重试；对不支持幂等键的外部系统，先查后做（check-then-act）并配合对账。要点是区分"读"与"写"，对写操作默认不自动重试，除非能证明幂等。

### B6. 怎么检测和去除重复的工具调用？
在运行时维护最近调用的集合，键为"工具名加规范化参数的哈希"，在同一运行内重复出现就拦截或提示模型；对有副作用的调用，用幂等键保证外部只生效一次；对只读调用可以缓存结果（按租户和参数）。还要区分"合理的重复"（轮询状态）与"无进展的重复"，后者靠无进展检测和步数上限兜底。

### B7. 什么是闭环自纠错（self-correction）？怎么做才可靠？
让智能体在得到反馈后修正自己：工具报错、校验器不通过、测试失败、评审意见。可靠的做法：反馈要**客观**（编译器、测试、模式校验、查询的 EXPLAIN、干运行结果），而不仅是模型"再想想"；每轮把具体的失败信息带回上下文；限制重试次数并在多次失败后改变策略或升级；记录每轮的差异避免原地打转。研究和实践都显示，没有外部信号的纯自我反思收益有限，甚至会把对的答案改错。

### B8. 什么是独立验证（independent verification）？怎么实现？
由与执行者相互独立的机制来检查结果，避免"自己给自己打分"。方式：确定性校验（测试、类型检查、模式、业务规则、对账）；独立的验证器模型或智能体，使用不同的提示、必要时不同的模型，且只看证据（工具输出、日志）而不是执行者的自述；多数表决；对关键结论要求引用来源并核对。要特别验证"智能体声称做了什么"与"追踪里实际发生了什么"是否一致（例如它说已发送邮件，但没有对应的工具调用记录）。

### B9. 对不可逆或高风险操作（删除数据、转账、对外发送）应该怎么处理？
分级：只读和可逆操作自动执行；不可逆操作默认需要人工审批；先产出**预览**或干运行（dry run）并让人确认；采用"提议—批准—执行"的两步流程，并把批准绑定到具体的参数（防止批准后被替换）；加限额、延迟生效窗口和撤销机制；使用独立、权限受限的执行器。实际上还要限制"一轮中能执行的高风险操作数量"，防止被诱导批量操作。

### B10. 提示注入（prompt injection）是什么？为什么对智能体特别危险？
攻击者把指令藏在模型会读到的内容里（网页、邮件、文档、工具返回），诱导模型偏离用户意图。对聊天机器人最多是输出错误；对智能体，模型能调用工具，注入可以变成真实的动作（泄露数据、发邮件、删文件）。被广泛引用的概念是"致命三要素"（lethal trifecta）：同时具备**访问私有数据**、**接触不可信内容**、**有对外通信能力**时，就可能被外泄数据。防御的核心是破坏其中至少一个要素。

### B11. 有哪些防御提示注入的设计模式？
没有任何一个能靠提示词"完全"解决，要靠架构：权限最小化；把不可信内容与高权限能力隔离（例如双模型模式：特权模型不直接接触不可信内容，由隔离的模型处理并只返回受限的结构化结果）；先规划后执行（计划在接触不可信内容之前固定，工具选择不受后续内容影响）；动作选择器（只允许从预设动作里选，不让不可信内容影响参数）；限制出口（网络白名单、禁止任意 URL 和图片渲染外泄）；对敏感动作人工确认；对检索内容标记来源并降级信任；红队测试集持续回归。

### B12. 如果智能体需要抓取外部网页再据此行动，如何设计安全边界？
把抓取到的内容当作不可信数据：放入明确的数据区域并声明"只作为资料，不作为指令"（这只是辅助，不是安全边界）；处理这类内容的步骤不持有高权限工具和私有数据；出口网络白名单与出站内容检查；输出不渲染可外泄的链接或图片；对后续动作加人工确认；记录来源用于审计。核心思想是**能力隔离**，不是"让模型别上当"。

### B13. 什么是"过度授权"（excessive agency）？
OWASP 的 LLM 应用风险之一：赋予智能体过多的功能、权限或自主性，导致被诱导或出错时造成过大破坏。对策：最小化工具集；工具本身的权限最小化；在下游系统而不是在模型里做授权；高影响动作的人工确认；限制自主性（预算、步数、范围）。

### B14. 怎么限制智能体的成本和失控风险？
多层预算：单次运行的最大步数、最大 token、最大费用、最大墙钟时间；每租户每日预算与速率限制；工具调用次数上限（特别是昂贵或有副作用的）；对异常的成本增长做告警和自动熔断；对重复循环做检测。要能回答"如何避免一次失控的运行烧掉大额费用"：核心是硬性上限加实时计量加告警，而不是事后看账单。

### B15. 工具超时、取消和部分失败怎么处理？
每个工具有独立超时，并区分"建立连接超时"和"总耗时超时"；取消要能传播到下游（取消令牌、关闭连接），避免僵尸任务；并行调用中部分失败时，决定是整体失败、返回部分结果还是由模型决定；超时后结果未知的有副作用操作，不能直接重试，要先查询确认。

### B16. 怎么给智能体设计"升级到人"的路径？
触发条件：置信度低、校验多次失败、命中高风险策略、超出预算、用户明确要求。升级时要把完整上下文交接给人（目标、已做的步骤、当前状态、失败原因、建议的下一步），并允许人处理后让智能体恢复继续。要衡量升级率和升级后的解决率，作为系统质量指标。

### B17. 如何让模型对工具结果保持"事实依据"，减少编造？
要求关键结论引用具体工具输出；对数字和标识符通过程序校验而不是让模型转述；把复杂计算交给工具（计算器、代码执行）；检索结果带来源；让模型在不确定时可以说"不知道"或请求更多信息，并在评测里奖励这种行为；对"声称已完成"的断言用追踪核对。

### B18. 怎么设计一个工具调用的"策略引擎"（policy engine）？
把授权规则从提示词里抽出来，放到独立组件：输入是（主体、动作、资源、上下文、风险等级），输出是允许、拒绝或需要审批。规则用声明式的策略语言（如基于属性的访问控制 ABAC 或关系型的访问控制），可测试、可审计、可热更新。运行时在每次调用前强制检查，所有决策记录日志。这样即便模型被注入，也越不过策略。

### B19. 怎么看待"让模型自己决定是否调用工具"与"强制调用"？
大多数框架支持自动（auto）、必须调用某个工具、禁止调用等模式。对于流程里必须发生的步骤（比如先做权限校验或先检索），用代码强制，不要寄希望于模型"想起来"。对开放式任务让模型自主选择，但要限制可选集合。

### B20. 工具太多时模型选错工具怎么办？
减少并合并工具；按场景动态加载工具子集（先路由再暴露）；清晰区分名称和描述，给出何时用何时不用；用检索从大工具库里选出候选；用评测衡量工具选择准确率并迭代描述；对相似工具用参数而不是多个工具来区分。

## C. 评估与评测体系（Evals & Test Harnesses）

### C1. 为什么非确定性的 LLM 系统需要专门的评测体系？"LLM 是非确定性的"算好答案吗？
不算。只说"非确定性"等于放弃了回归工程。好的回答是：把含糊的质量目标转成**有代表性的测试集**、**可信的评分器**、**线上监控**和**可辩护的发布或回滚决策**。非确定性意味着要用统计方法（多次运行、置信区间、通过率）而不是单次断言；而其余大量部分（工具调用、状态转移、校验）本来就是确定性的，应该用传统测试覆盖。

### C2. 一条完整的评测流水线包含哪些环节？
数据集（带版本）→ 被测系统的运行（可复现的配置：提示词、模型、工具、检索）→ 评分（代码规则、LLM 评审、人工）→ 聚合与报告（分项指标、置信区间、与基线的对比）→ 门禁（CI 里设置阈值，不过不合并）→ 线上监控与回流（把线上失败案例补进数据集）。要强调开发期、发布前和线上使用同一批评分器，分数才具可比性。

### C3. 如何构建回归测试集？
来源：真实的线上日志（脱敏）、人工整理的典型与边界场景、已知的失败案例（每次线上事故都沉淀一条）、合成数据（谨慎使用并抽检）、红队样例。要版本化、有分层（按功能、难度、风险）、标注期望的约束和判定标准（没有期望约束的提示只是演示，不是回归测试）。要防止数据泄漏到提示词或微调数据里，并定期淘汰过时样例。

### C4. 什么是 LLM-as-a-judge？优缺点和使用要点？
用一个模型对另一个模型的输出按量规（rubric）打分或做两两比较。优点：可扩展、能评估语义质量；缺点：有偏差、可能不稳定、有成本。要点：①先验证评审员——用人工标注的黄金集衡量一致性（例如用 Cohen's kappa，常见做法是要求与人工高度一致后再大规模使用）；②量规具体、拆成多个二元或小量程的判断；③让评审员先给理由再给分；④温度设低、固定评审模型版本；⑤能用代码规则判定的优先用代码；⑥定期抽检。

### C5. LLM 评审员有哪些常见偏差，怎么缓解？
位置偏差（偏爱先出现的答案）：两两比较时交换顺序再取一致；冗长偏差（偏爱更长的回答）：在量规里明确不奖励长度，或做长度控制；自我偏好（偏爱同家族模型的输出）：用不同家族的模型做评审；对格式和语气的偏好；对事实的轻信（评审员没有证据时可能被说服）：给评审员提供参考资料或检索到的上下文；评审模型升级导致分数漂移：固定版本并在升级时重新校准。

### C6. 怎么评估一个智能体，而不仅是最终答案？
多层次：**结果**（任务是否真的完成，最好直接检查环境的最终状态，例如数据库的内容，而不是看模型怎么说）；**轨迹**（步数、是否有冗余或重复调用、工具选择与参数是否正确、是否从错误中恢复）；**安全**（是否越权、是否被注入、是否触碰禁区）；**成本与延迟**（单次任务的 token、费用、耗时）；**一致性**（同一任务多次运行的稳定性）。以会议预订智能体为例：检查日历里最终是否出现了正确的会议（时间、参与人、时区），而不是只看它回复"已预订"。

### C7. 什么是 pass@k 和 pass^k？
pass@k：k 次尝试中**至少一次**成功的概率，衡量能力上限；pass^k：k 次尝试**全部**成功的概率，衡量可靠性。对面向用户的生产智能体，后者更重要——一个单次成功率 90% 的智能体，连续 8 次都成功的概率只有约 43%。（pass^k 常见于智能体基准 τ-bench 的讨论。）

### C8. 如何为智能体构建可复现的测试环境？
模拟环境：用沙箱化的工具后端和固定的初始状态（假的数据库、模拟的 API），每个测试从干净状态开始；工具录制与回放（record/replay，类似 VCR 的做法）使单元测试不依赖外部服务；用户模拟器（由模型扮演用户）跑多轮对话；对不可避免的外部依赖设置合约测试。分两类测试：**不调用真实模型**的测试（编排逻辑、状态机、重试、护栏，用桩模型，完全确定）和**调用真实模型**的评测（统计性）。

### C9. 如何检测幻觉（hallucination）？
对有依据的任务（检索增强、工具结果）：**忠实度（faithfulness/groundedness）**检查——把答案拆成原子论断，逐条验证是否被来源支持（可用蕴含判断模型或评审员），并检查引用是否真实存在；对无依据的开放问答：自一致性（多次采样看是否矛盾）、与权威来源对比、拒答能力评测。对智能体还要查"声称的动作"与追踪是否一致。常见的坑：评审员没拿到检索上下文就判幻觉，会得到错误结论。

### C10. 如何评估检索增强生成（RAG）？
分开评：**检索**（召回率、命中的排名、噪声比例，用带标注的相关文档集）与**生成**（忠实度、答案相关性、完整性、引用正确）。再加端到端的任务成功。要有权限相关的测试（用户不应检索到无权访问的文档）、时效性测试（更新或删除的文档）、冲突资料的处理测试。

### C11. 如何在 CI 里做回归门禁，又不被随机性拖垮？
对确定性部分严格断言；对统计性评测：固定随机种子（不保证）、对每个样例多次运行、按通过率与基线比较并设置容忍区间、用置信区间或配对检验判断差异是否显著、对关键样例（安全相关）要求全过；把昂贵的评测分层（冒烟集在每次提交跑，完整集在夜间或发布前跑）；失败时输出差异样例便于排查；缓存无变化部分的结果以节约成本。

### C12. 如何做线上评测与监控？
对采样的生产流量跑评分器（异步，不影响延迟）；监控任务成功率、升级率、用户负反馈、工具错误率、轨迹长度、成本；影子（shadow）运行新版本并比较；灰度与 A/B；对发布决策用"新版本能否在不增加关键错误、延迟或每个已解决案例成本的前提下替代旧版本"来表达；把失败案例回流到数据集。

### C13. 如何评估评审员本身？
准备人工标注的黄金集（包含边界案例），计算与人工的一致率或 kappa；分析混淆矩阵（哪些类型误判）；做对抗测试（冗长但错误的回答、格式漂亮但内容错的回答）；检查对顺序和长度的敏感性；监控评审员分数分布的漂移。一个可参考的做法是在规模化前要求与人工标签达到较高一致（有指南建议大约 75% 到 90% 的区间，具体门槛取决于任务，请自行判断）。

### C14. 基准测试（benchmarks）能说明什么，不能说明什么？
公开基准（如软件工程类的 SWE-bench、智能体类的 τ-bench、网页类的 WebArena、通用助理类的 GAIA、终端任务类的 Terminal-Bench 等）有助于比较模型的大致能力，但与你的业务场景、工具和数据分布不同，可能存在污染和过拟合。最终要靠**自己的、贴近业务的评测集**做决策。

### C15. 评测集太小或者标注成本太高怎么办？
先用小而精的集合覆盖关键场景和失败模式；用线上日志持续扩充；用合成数据放大但要抽检；用评审员加人工抽检的组合；对高风险场景用确定性规则；优先标注"模型和基线分歧大"的样例（主动学习）以提高信息量。

### C16. 如何评估提示词或模型的修改是否真的更好？
在同一数据集上配对比较新旧版本；报告分项指标而不是只给一个平均分；用多次运行和显著性检验；看关键切片（高风险、长尾）是否退步；同时看成本与延迟；通过影子或灰度再验证。避免"改了一个失败样例就合并"的做法——容易引起其他样例的回归。

### C17. 如何测试护栏和安全行为？
准备红队套件：提示注入样例（直接与间接）、越权请求、数据泄露诱导、危险动作诱导；断言**运行时的强制措施**确实拦截（比如被拒绝的工具调用、被截获的外发请求），而不是只看模型的回答；对策略引擎做单元测试；把新发现的攻击样例加入回归；定期更新攻击库。

### C18. 评测中"用户反馈"和"人工评审"怎么用？
用户反馈（点赞、纠正、重新生成、升级到人）是廉价的线上信号，但有偏差（只有极端的用户会反馈）；人工评审用于校准评审员、评估新场景和仲裁争议。两者互补：自动评分器负责规模，人工负责校准与盲点发现。要为评审者提供清晰的指南和一致性检查。

## D. 分布式系统与后端工程

### D1. 为什么智能体需要"持久化执行"（durable execution）？
智能体运行时间长、步骤多、依赖外部服务，进程会崩溃、会部署重启、会遇到超时和限流。持久化执行的核心思想是：**运行的进度保存在运行进程之外**，崩溃或重启后从最近完成的位置继续，而不是从头再来。否则，崩溃后重跑会重复已有副作用（再次退款、重复发邮件）并浪费昂贵的 LLM 调用。

### D2. Temporal 的核心模型是什么？
**工作流（workflow）**是确定性的编排代码，**活动（activity）**是可能失败、有副作用的具体工作（调用 LLM、调用工具、访问数据库）。Temporal 把工作流的每个事件写入事件历史（event history）；工作进程崩溃后，由新的进程**重放（replay）**历史来重建工作流的状态，已完成的活动不会重复执行，而是直接取回记录的结果。另有信号（signal，异步外部输入）、查询（query，只读状态）、更新（update）、定时器、子工作流、重试策略与超时。把智能体映射上去：编排循环是工作流，每次 LLM 调用和工具调用是活动。

### D3. 工作流代码为什么必须是确定性的？LLM 调用怎么办？
重放要求同一份历史产生同样的命令序列，所以工作流代码里不能直接用随机数、当前时间、网络或线程。LLM 调用本身是非确定性的，因此要放进**活动**里，结果被记入历史，重放时直接读取记录的结果而不是再次调用模型。这也是"LLM 输出要作为事件持久化"的原则：保证恢复后的行为与崩溃前一致。

### D4. 事件历史会越来越长怎么办？
历史有大小和事件数的上限（量级在几万条事件），长期运行的智能体需要"继续为新的运行（continue-as-new）"：在适当的时候带着精简后的状态开启新的运行，让历史重置。设计上要决定哪些状态需要带过去（压缩后的上下文、待办、已完成摘要）。也可以把大对象放到外部存储，历史里只放引用。

### D5. 工作流和代码如何升级而不破坏正在运行的任务？
运行中的任务已有历史，新代码的行为必须与旧历史兼容，否则重放会出现不一致。做法：用版本机制（补丁标记或工作进程版本固定）让旧运行继续用旧逻辑、新运行用新逻辑；避免随意改变活动顺序；用"固定在某版本"的部署策略并逐步淘汰旧版本。对提示词和模型版本同理，运行中的任务通常固定在启动时的版本。

### D6. 除了 Temporal，还有哪些选择？怎么选？
同类的持久化执行：DBOS、Inngest、Restate 等；智能体框架自带的检查点：LangGraph 的检查点（把图状态存到数据库，支持暂停恢复）；基于消息队列自己搭建的状态机。选择取决于：需要多强的恢复语义、运维复杂度、团队熟悉度、语言支持、是否要跨语言、规模。要说明区别：检查点是"保存状态"，而 Temporal 类是"保存执行历史并重放"，对副作用的处理和恢复保证不同。

### D7. Argo Workflows 适合做什么？和 Temporal 有什么区别？
Argo Workflows 是 Kubernetes 原生的工作流引擎，用自定义资源描述有向无环图或步骤，每个步骤通常是一个容器，适合批处理、机器学习流水线、数据处理。它偏向"编排容器任务"，延迟较高、粒度较粗；Temporal 是代码优先、细粒度、低延迟的持久化执行，适合业务逻辑复杂、需要长时间等待和人工交互的流程。智能体的单步 LLM 调用用 Argo 编排通常太重，但"夜间跑评测"之类的批任务很合适。

### D8. RabbitMQ 和 Kafka 有什么区别？各自适合智能体系统的什么场景？
RabbitMQ 是传统消息代理：交换机（exchange）按规则路由到队列，消费者竞争消费，确认（ack）后消息删除，支持优先级、延迟与死信交换机，适合**任务分发和请求—响应**式的工作队列；Kafka 是分布式提交日志：主题分区、消息保留、消费者组按偏移量读取，可重放，吞吐极高，适合**事件流、审计日志、流处理、多消费者订阅**。智能体里：任务队列和工具执行分发可以用 RabbitMQ 或云队列；追踪、事件、评测数据管道用 Kafka。

### D9. 消息系统里怎么保证"不丢、不重、有序"？
不丢：生产者确认、持久化与多副本、消费者处理完再确认；不重：网络层面做不到严格的恰好一次，要靠**幂等消费**（去重键、唯一约束）；有序：Kafka 在分区内有序，用业务键做分区键保证同一键的顺序；RabbitMQ 在单队列单消费者时有序，多消费者并发会打乱。对智能体运行，常用"每个运行编号映射到同一分区或同一工作流实例"来做单写者串行。

### D10. 毒丸消息（poison message）和死信队列（dead-letter queue）怎么处理？
某条消息总是处理失败，会无限重试并阻塞队列。做法：限制重试次数并用退避；超过后转入死信队列并告警；保留原始内容和失败原因以便排查、修复后重放；对智能体任务，还要保证失败状态对用户可见，而不是静默丢失。

### D11. 在高并发下，如何管理成千上万个同时运行的智能体？
大多数时间智能体在等待 LLM 或工具的 IO，所以用异步和事件驱动，而不是一个线程一个智能体；限制并发：每租户、每工具、每模型供应商的并发与速率上限；队列加公平调度（避免大租户饿死小租户）；隔离舱（bulkhead）防止一个慢依赖拖垮整体；对供应商速率限制（每分钟请求数和 token 数）做客户端侧的令牌桶；背压：队列满时拒绝或排队，而不是无限堆积；水平扩展无状态工作进程。

### D12. 智能体运行时的一致性问题有哪些？
**同一运行的串行化**：同一时刻只能有一个工作进程推进某个运行（用分区键、工作流编号、租约加围栏令牌、或带版本号的乐观锁）；**僵尸工作进程**：旧工作进程以为自己仍持有租约而继续写入，用围栏令牌（单调递增的令牌）让存储拒绝旧令牌的写入；**并发工具调用写共享状态**：用 reducer 或合并语义；**读写一致**：用户刚提交的审批要被恢复的运行立即看到。

### D13. 崩溃恢复（crash recovery）的设计要点是什么？
①状态每一步落盘（或事件溯源）；②有副作用的操作遵循"先记录意图 → 执行（带幂等键）→ 记录结果"；③恢复时检查"有意图无结果"的步骤，先向下游查询（用幂等键）判断是否已生效，再决定补记、重试或补偿；④心跳与租约检测工作进程死亡，由其他进程接管；⑤对无法确认的情况标记为"需对账"，转人工或自动对账；⑥重放时不再调用模型，而是读取已记录的输出。典型反例：智能体调用了支付接口但在保存结果前崩溃，重启后重复退款。

### D14. 怎么选择检查点（checkpoint）粒度？
太粗：崩溃后重做的工作多，重复昂贵调用；太细：写入开销大、存储膨胀、延迟增加。常见折中：在每次 LLM 调用之后、每次有副作用的工具调用前后各落一次；对大对象只存引用。要衡量恢复时间目标和写入成本，并对状态做压缩与定期清理。

### D15. 智能体运行的数据模型怎么设计？
典型表：运行（run：编号、租户、状态、版本、预算、创建与结束时间）、步骤（step：序号、类型、输入、输出引用、状态、尝试次数、耗时、token 与费用）、事件（append-only 的事件日志）、待审批（approval）、产物（artifact 引用）。用 Postgres 的事务保证状态与发件箱（outbox）一致；JSONB 存半结构化内容；按时间或租户分区；大文件进对象存储。事件日志使得回放、审计和调试更容易。

### D16. 如何让"状态更新"和"对外发消息"保持一致？
用事务发件箱模式（transactional outbox）：在同一个数据库事务里写状态和待发送的事件，再由独立的进程可靠地发布；消费者做幂等处理。避免"先更新数据库再发消息"（可能消息丢失）或"先发消息再更新数据库"（可能状态丢失）。

### D17. 如何处理长时间的人工等待和外部事件？
不占用进程：持久化状态后释放资源；用定时器和事件（信号、回调、消息）唤醒；设置超时与升级；等待期间要处理"上下文已经变化"（例如价格变了、权限被撤销）的重新校验。持久化执行引擎天然支持这类等待；自己实现则要有可靠的唤醒与幂等恢复。

### D18. 如何设计一个让客户"自带智能体"的运行平台？
关键维度：隔离（每个租户和每次运行的沙箱、网络和凭证）、调度（队列、并发、公平）、持久化（运行状态与事件）、资源与预算（CPU、内存、token、费用、时间）、可观测（追踪、日志、指标）、治理（权限、审计、版本）、开发者体验（SDK、本地调试、回放）、成本核算。要说明编排器无状态、状态外置，任何实例可加载状态并从最后完成的步骤继续。

### D19. Python 的异步编程在智能体服务中要注意什么？
事件循环不能被阻塞：CPU 密集或阻塞 IO 要放进线程池或进程池；用结构化并发（`asyncio.TaskGroup`，Python 3.11+）管理子任务的生命周期和异常传播；用信号量限制并发；正确处理取消（`CancelledError` 应该向上传播，清理资源）；为所有外部调用设置超时；避免在协程里使用同步的客户端库；流式响应用异步生成器；注意任务泄漏（创建了没人等待的任务）。

### D20. Python 的全局解释器锁（GIL）对智能体服务有影响吗？
智能体服务多为 IO 密集（等 LLM 和工具），异步或线程就够，GIL 影响小；CPU 密集的部分（解析大文件、向量计算、序列化）要用进程池、原生扩展或放到其他服务。Python 3.13 起提供实验性的无 GIL 构建，更新的版本继续演进，但生态兼容性需要评估。

### D21. 为什么底层运行时或网关常用 Go 或 Rust？
网关和运行时要处理大量并发连接、流式转发、低且稳定的延迟、静态二进制部署。Go：goroutine 与通道使并发简单，标准库的网络能力强，编译快，运维友好，有垃圾回收但对多数场景足够；Rust：无垃圾回收、内存安全、极致性能与可预测的延迟，但学习曲线陡，开发速度较慢。常见分工：Python 负责 AI 管道和业务编排，Go 或 Rust 负责网关、沙箱控制面、数据平面。

### D22. 部分场景用到 C# 或 Elixir，怎么理解？
C#：微软生态下（如 Semantic Kernel、Azure）企业开发常用，类型系统和异步支持成熟。Elixir（运行在 Erlang 虚拟机 BEAM 上）：轻量进程、消息传递、监督树和"让它崩溃"的容错哲学，非常适合大量长生命周期、需要容错的会话式进程，也就是"一个智能体一个进程"的模型。面试中不需要精通，但要能说出各自的适用性。

### D23. 一个 LLM 网关（gateway）应该提供哪些功能？
统一的多供应商接入与协议适配；认证与租户识别；速率限制与配额（请求与 token）；预算与计费计量；路由与降级（按模型、成本、延迟、可用性）；重试与熔断；流式转发；响应与提示缓存（注意租户隔离）；护栏（敏感信息脱敏、策略）；日志与追踪（注意隐私）；密钥管理。自研要权衡运维成本，也可以基于开源方案。

### D24. 如何应对 LLM 供应商的限流和故障？
客户端侧令牌桶对齐供应商的限制；遇到 429 或 5xx 用指数退避加抖动，并尊重 `Retry-After`；多供应商或多区域的故障切换；对非实时任务用批处理接口降低成本；队列平滑突发；对降级路径做评测（备用模型的质量）；熔断避免雪崩。

### D25. 缓存在智能体系统里有哪些层次？风险是什么？
提示前缀缓存（供应商提供，降低重复前缀的成本和延迟，要求把稳定内容放在前面）；工具结果缓存（只读、可缓存的调用）；语义缓存（相似问题复用答案）；检索结果缓存。风险：**跨租户泄漏**（缓存键必须包含租户、权限、策略版本、数据分类等维度）、陈旧数据、缓存了带副作用或个性化的结果。默认对高敏感流量关闭共享缓存。

### D26. 如何设计智能体任务的幂等提交？
客户端提交任务时带幂等键；服务端用唯一约束保存键与任务的映射，重复提交返回同一个任务；任务状态机保证转移幂等；回调和 Webhook 也带去重编号。要回答"用户连点两次"和"客户端超时后重试"的场景。

## E. 安全、租户隔离与可观测性

### E1. 面向大企业客户的多租户智能体平台，租户隔离（tenant isolation）要覆盖哪些层？
要覆盖整条链路，不只是数据库：**身份与授权**（每个请求携带租户和用户身份，授权在数据和工具层强制）、**数据**（存储、向量索引、缓存、文件）、**计算**（沙箱）、**网络**（出口控制）、**密钥与凭证**、**缓存**、**日志与追踪**（可能的侧信道泄漏）、**配额与速率**（防止吵闹邻居）、**加密密钥**（可选的按租户密钥）。核心原则：**隔离由平台在数据层和身份层强制执行，而不是写在系统提示里**。

### E2. 向量检索（RAG）里怎么防止跨租户数据泄漏？
向量相似度只关心语义，不关心权限，所以不能靠提示词让模型"只用本租户的数据"。要在检索层强制过滤：按租户使用独立的索引或命名空间，或者在查询里附加**硬过滤条件**（由服务端注入，不接受模型或用户提供的租户参数）；更细粒度时按文档级权限（ACL 或基于属性的访问控制）过滤；写入时也要打上正确的租户和权限标签；对检索后的结果再做一次授权校验。有研究报告称，在检索层做基于属性的访问控制可以消除跨租户泄漏，并只增加很小的延迟，这属于单篇论文的结论，需要独立复现，请谨慎引用。

### E3. 智能体执行代码或操作文件时，沙箱（sandbox）怎么设计？
每个租户（最好每个任务）使用隔离的执行环境：轻量虚拟机（如 Firecracker 微虚拟机）、用户态内核（如 gVisor）或带 seccomp 的容器，权衡隔离强度与启动速度；资源限制（CPU、内存、磁盘、进程数、运行时间）；只读根文件系统，工作目录临时；**默认无网络**，需要时只允许白名单出口；凭证不放进沙箱，由外部代理在受控下注入并限定范围和有效期；任务结束销毁环境，避免持久沙箱里的信息在会话之间残留；日志和产物按租户存放。

### E4. 什么是"混淆代理"（confused deputy）问题？在智能体里怎么出现？
一个高权限的组件被低权限的一方诱导，代为执行其无权做的事。智能体常用一个权限很大的服务账号调用工具，用户通过对话诱导它访问了自己无权看的数据。解决：用"代表用户"的凭证（如令牌交换，获取范围受限、短时有效的用户身份令牌）调用下游，让下游系统按**用户**的权限授权。

### E5. 如何管理智能体使用的凭证和密钥？
不放入提示词、上下文或日志；由运行时或代理在调用时注入；使用短期、最小范围的令牌，支持吊销；用密钥管理服务；按租户隔离；对工具的 OAuth 授权要有范围审查和用户同意；定期轮换；审计每次使用。

### E6. 日志和追踪会成为泄漏渠道吗？
会。追踪里常含提示词、检索内容和工具返回的敏感数据。对策：按租户隔离存储与访问控制；对敏感字段脱敏或只存摘要和哈希；可配置的保留期与删除；访问审计；对用户可见的追踪只展示本人的数据；遵守数据驻留要求。

### E7. 如何防止一个租户的负载影响其他租户（noisy neighbor）？
每租户的并发、速率、token 与预算配额；队列的公平调度（加权公平队列）；隔离舱；资源配额；对重度用户限流并给出明确的错误；对关键租户可预留容量；监控每租户的使用并告警。

### E8. 治理（governance）与审计需要什么？
完整的审计轨迹：谁（用户、智能体、服务）在什么时候、用什么版本的提示词与模型、调用了哪个工具、参数和结果摘要、审批人是谁；变更管理（提示词、工具、模型的版本与评审）；数据分类与保留策略；合规报告（如访问记录）；对高风险动作的审批留痕；可导出和不可篡改（追加写）的存储。

### E9. 如何搭建智能体的可观测性（observability）？
三类信号：**追踪（trace）**：一次运行是一条 trace，每次模型调用、工具调用、检索、审批是一个 span，带输入输出摘要、耗时、token、费用、模型与提示词版本；**指标（metrics）**：任务成功率、延迟分位数、每步耗时、token 与费用、工具成功率、轨迹长度、循环触发次数、升级率、队列深度、供应商错误率；**日志**：结构化，带运行编号。再加告警与仪表盘、按租户切片、回放能力。可以参考 OpenTelemetry 的生成式 AI 语义约定（相关规范仍在演进），并配合 LangSmith、Langfuse、Arize Phoenix、Braintrust 等工具。

### E10. 你会为智能体设置哪些告警？
成本异常（单次运行或租户的 token 与费用突增）；循环或重复调用比例上升；任务失败率与超时率；工具错误率；供应商错误与限流；队列积压；审批等待超时；护栏被触发的次数异常（可能是攻击）；评分器的在线分数下降；敏感数据检测命中。告警要带上下文（运行编号、租户、版本）便于排查。

### E11. 如何定位延迟瓶颈？
看 trace 的火焰图或瀑布图，把延迟分解为：排队时间、模型首个 token 时间（TTFT）、生成时间（与输出长度相关）、各工具耗时、检索耗时、重试和退避、步数。常见优化：并行独立的工具调用、减少不必要的模型往返、缩短提示词和利用前缀缓存、把简单步骤交给小模型、流式输出、预取数据、限制输出长度。

### E12. 如何追踪每次调用的 token 消耗和费用？
在网关或 SDK 层统一计量：每次调用记录输入、输出、缓存命中的 token（供应商的响应里通常包含用量）；按运行、租户、功能、模型汇总；按价格表换算费用；设置预算和实时告警；区分重试和并行产生的重复消耗；定期对账供应商账单。

### E13. 在生产里调试"智能体行为异常"的方法？
先重现：用运行的 trace 和记录的模型输出**回放**；定位偏离点：是哪一步的哪个模型调用或工具结果开始不对；检查输入（提示词与上下文是否被污染、检索是否错误、工具返回是否异常）；比较成功与失败运行的差异；用最小化的样例加入回归集；修复后在评测集和影子流量上验证。对"反复调用同一工具"的案例，重点检查工具返回是否提供了可操作的信息、终止条件是否明确、循环检测是否生效。

### E14. 数据保留、隐私与合规方面要考虑什么？
对个人信息的分类与最小化；训练数据使用的承诺（供应商侧是否用于训练，零数据保留选项）；数据驻留与跨境；删除请求要覆盖对话、记忆、向量索引、缓存、备份和日志；对敏感字段的加密；对员工访问的审计。要能回答"客户要求删除其所有数据"的完整链路。

### E15. 企业客户（如财富 500 强）会特别关心哪些安全问题？
数据不泄漏和不被用于训练；租户隔离证明（架构评审、渗透测试、合规报告）；单点登录与细粒度权限；审计日志；数据驻留；私有网络连接；可自带密钥；供应商风险（模型供应商和工具）；事件响应与通报；可控的智能体自主性（审批、预算、范围）；评测与红队结果的可见性。

## F. AI 原生研发工具链

### F1. 你日常怎么使用 Claude Code、Cursor、Windsurf、GitHub Copilot 这类工具？
这类题看你是"重度使用者"还是"调包侠"。要具体：说清楚你在什么任务上用哪个工具、怎么给上下文、怎么验证输出。例如：用智能体模式做跨文件重构；先让它出计划再执行；用项目说明文件（如 Claude Code 的 `CLAUDE.md`、Cursor 的规则文件）固化代码规范与常用命令；用子智能体隔离调研类任务；用钩子（hooks）强制执行格式化与检查；用 MCP 连接内部工具；用权限模式控制它能自动做什么；用 git worktree 并行跑多个智能体。要承认局限，并说出你的验证习惯。

### F2. 如何用 AI 工具快速消化一个陌生的大型遗留代码库（legacy codebase）？
步骤：①先让工具生成**架构地图**（目录结构、入口、模块职责、数据流、依赖），你再对照验证；②沿一个具体的用户场景追踪调用链（从接口到数据库）；③读测试和配置、构建与部署脚本；④为不熟悉的行为编写**特征化测试（characterization tests）**，把现有行为固定下来，再动手改；⑤小步修改、每步跑测试；⑥让工具解释"为什么这样写"并回溯提交历史和文档；⑦始终对关键结论做人工核对，因为工具可能编造不存在的函数或误解业务意图。

### F3. 如何验证 AI 生成的代码，防止"看起来对"？
以测试为准绳：先写或补测试，再让 AI 实现；运行类型检查、静态分析、安全扫描；阅读差异（不只看通过）并质疑假设；检查它引用的 API 是否真实存在；对性能与并发敏感的代码做专项评审；对数据迁移、权限等高风险改动要求人工评审；小步提交便于回滚。要强调"生成容易，验证才是工作量"。

### F4. 如何构建自主的工程流水线（autonomous engineering pipeline）？
典型形态：事件触发（工单、失败的 CI、定时任务）→ 智能体在沙箱里拉代码、定位问题、修改、跑测试 → 自动开合并请求 → CI 校验 → 人工评审后合并。要点：隔离的执行环境、受限的权限（只能推到特定分支）、预算和时间限制、结果必须通过确定性校验（测试、类型、安全扫描）、完整追踪、失败时的回退与通知、对提示注入的防御（仓库内容可能带恶意指令）、衡量指标（合并率、返工率、回归率、每个合并请求的成本）。

### F5. 让智能体改代码有哪些常见风险？
编造或误用 API；过度修改（大范围重写）；破坏隐含约定；引入安全漏洞；把秘密写进代码或日志；提示注入（读到恶意的 README 或依赖说明后执行危险命令）；许可证问题；改了测试来"通过"（作弊）。对策：限制权限与范围、强制评审、禁止修改特定文件（如测试配置和流水线）、审计命令执行。

### F6. 怎么给 AI 编码工具设置项目级的上下文？
写清楚构建、测试、运行命令；目录结构与模块职责；编码规范和禁忌；常见陷阱；架构决策记录的入口；不要写成冗长的百科——内容要精炼、可验证，并随代码更新。分层放置（根目录与子目录各有说明）。定期用实际任务检验这些说明是否有效。

### F7. 什么任务适合交给 AI 智能体，什么不适合？
适合：边界清楚、可被自动验证（有测试）的任务，机械重构，迁移，写测试，文档，代码探索与解释，原型。不适合：需求含糊、需要深层业务判断、没有验证手段、涉及高风险与不可逆操作、需要对系统全局做取舍的架构决策。常用做法是"人负责定义问题与验收，智能体负责执行与初步验证"。

### F8. 并行使用多个编码智能体时要注意什么？
用独立的工作树或分支避免互相覆盖；明确划分任务边界避免冲突；合并时处理冲突和重复修改；控制总成本；对每个结果各自验证；汇总时检查它们对共享接口的假设是否一致。

## G. 软技能与工程判断（Senior IC）

### G1. 讲一个你在高度模糊的需求下独立把事情做成的例子。
用 STAR（情境、任务、行动、结果）结构，但要突出资深 IC 的特点：你如何把模糊目标转成**可验证的成功标准**；如何缩小范围、定里程碑；如何做出关键取舍并与干系人对齐；如何用数据（评测、实验）而不是直觉推进；结果用业务指标和可靠性指标表达；你从中学到什么、现在会怎么改进。

### G2. 产品经理说"我们要做一个会自己处理工单的 AI 智能体"，你怎么开始？
先澄清：要解决的是哪类工单、当前人工处理的成本与质量、成功的定义（解决率、准确率、客户满意度、成本）、错误的代价与不可接受的行为、数据与系统权限现状、合规要求。再分阶段：先做**只读的辅助**（给建议、人工确认），收集数据和评测集；再做低风险类别的自动处理；逐步扩大自主范围，每一步用评测和线上指标证明。避免一上来就做全自动。

### G3. 你怎么判断一个需求该用智能体，还是普通工作流、规则或传统机器学习？
看确定性和成本：规则或代码能解决的就不要用 LLM；步骤固定、只有某一步需要语言理解，用工作流加一次 LLM 调用；只有路径不可预先确定、值得为灵活性付出成本时才用智能体。再看错误代价、延迟预算、可验证性。给出具体例子比抽象原则更有说服力。

### G4. 如何在"AI 的炫酷"和"系统稳定、低延迟、可运维"之间取舍？
把"炫酷"落到可衡量的用户价值上；对每个增加复杂度的设计（多智能体、反思循环、大模型）要求评测证据；设定延迟与成本预算，超出就简化；优先保证可观测、可回滚、有人工兜底；给自主性分级发放。要有一个说服团队的方式：用数据展示"更复杂的方案带来的增益和成本"。

### G5. 大模型和智能体的能力边界有哪些？
容易在长链条任务中累积错误（若每步成功率 95%，10 步全对的概率只有约 60%）；对不熟悉的领域和精确的数字、引用容易编造；对长上下文中的细节可能遗漏；对工具和环境反馈的利用依赖设计；对抗性输入下容易被操控；成本与延迟随步数增长；非确定性。所以要缩短链条、加验证、限制自主性、把确定性工作交给代码。

### G6. 描述一次生产事故或你亲手踩过的坑。你学到了什么？
选一个真实的、与可靠性或成本相关的案例：例如重试导致重复扣费、循环调用耗尽预算、检索泄漏了不该看的数据、提示词改动引起回归。讲清楚发现方式、影响范围、根因、临时止血、长期修复（幂等、预算、评测门禁、权限）、复盘机制。避免只讲成功故事。

### G7. 你如何做到"强 Owner 意识"但又不越权？
对结果负责：从需求到上线到运维到复盘，主动发现并补齐缺口（监控、文档、回滚方案）；遇到跨团队依赖，主动推动并明确升级路径；对不属于自己的决策，用数据和方案提出建议并让决策人明确决定；对风险及时透明地同步。要体现低自我（low ego）：愿意被挑战、公开承认错误、把功劳归于团队。

### G8. 你和同事或产品在技术方向上意见不一致，怎么处理？
先确认双方的目标和约束是否一致；把分歧转化为可验证的假设（做小实验、看数据、评测）；写简短的设计文档列出选项与取舍；允许"不同意但执行"，并约定回头复盘的指标；避免争论变成立场之争。

### G9. 作为没有管理职责的资深 IC，你如何放大影响力？
设计评审与技术方案的把关；沉淀可复用的组件和评测基础设施；写清楚的文档和示例；辅导他人（代码评审、结对）；推动工程规范（测试、可观测、事故复盘）；在模糊的问题上承担"定义问题"的角色。

### G10. 如何向非技术的干系人解释智能体的风险和局限？
用业务语言：说明"会在多大比例上出错、错了会怎样、我们怎么发现和兜底"；用具体例子而不是抽象术语；给出分阶段的上线计划和明确的退出标准；展示监控和审批机制；避免承诺 100% 准确。

### G11. 你怎么评估并引入一个新的框架或模型？
设定评估维度（质量、成本、延迟、稳定性、生态与维护状态、安全与合规、迁移成本）；在自己的评测集上做对比；做小范围试点；设计抽象层降低供应商锁定；明确回退方案；关注项目的维护状态（比如某些框架转入维护模式的风险）。

### G12. 你怎么估算一个智能体项目的工期和风险？
把不确定性高的部分（评测集、数据质量、工具接入、权限与合规）放在前面，用小的端到端原型尽早验证可行性；区分"能跑通演示"和"能上生产"的工作量（评测、护栏、可观测、恢复、运维通常占大头）；给出范围可变的里程碑；明确依赖和假设。

### G13. 常见的行为面试题（准备 3 到 5 个可复用的故事）
- 一次你推翻自己之前的技术决定的经历。
- 一次你为了稳定性而对"酷炫功能"说不的经历。
- 一次你在紧急事故中的角色。
- 一次你从零搭建某个基础设施并推动其被采纳。
- 一次你对错误的需求或指标提出异议。
每个故事准备好：背景、你的具体行动、数据化结果、反思。

## H. 系统设计与场景题

每题给出"回答骨架"，建议口头练习，用 45 分钟讲完。通用步骤：澄清需求与规模 → 核心流程与组件 → 状态与持久化 → 失败与恢复 → 安全与隔离 → 评测与可观测 → 成本与延迟 → 取舍与演进。

### H1. 设计一个让客户自带智能体代码的智能体运行平台（据报道的标准题之一）
**澄清**：客户数量与规模、智能体的运行时长、语言与框架、是否有人工审批、数据敏感度、SLA。
**骨架**：控制面（租户、智能体版本、配置、预算）与数据面（运行时）分离；提交运行 → 写入运行记录与事件 → 放入队列 → 无状态工作进程领取（租约加心跳）→ 在沙箱中执行智能体代码，所有外部调用（LLM、工具）通过网关；每步持久化；崩溃后其他工作进程接管；状态与产物外置（Postgres 加对象存储）。
**深入**：持久化执行（用 Temporal 一类，或自建事件日志）；多租户隔离（沙箱、网络出口、凭证注入、按租户缓存与配额）；公平调度与背压；追踪与计量；版本固定与灰度；本地调试与回放。
**追问**：智能体在追踪中途崩溃如何恢复；状态在编排器内存还是持久存储；一个租户跑飞了怎么办；如何防止一个租户读到另一个租户的数据。

### H2. 设计一个协调长时间运行、有人参与的工作流与自动化智能体的系统
**骨架**：工作流用状态机建模；智能体步骤是活动；人工步骤是"创建待办 → 持久化 → 等待信号"；通知渠道（邮件、聊天、应用内）；审批界面展示完整上下文与建议；超时与升级；恢复时重新校验；审计日志。
**深入**：几天后的恢复（版本固定、状态迁移）；审批与参数绑定；并发审批冲突；人工修改智能体产出后如何回灌；SLA 与提醒。

### H3. 设计一个企业客服或运维智能体，要调用订单、退款、知识库等内部系统
**骨架**：入口（鉴权、识别用户与租户）→ 意图路由 → 检索增强（带权限过滤）→ 工具调用（代表用户的凭证）→ 护栏（风险分级、审批阈值、幂等键）→ 回复与审计。
**深入**：退款等不可逆操作的"提议—批准—执行"；工具错误的处理；对话记忆与隐私；提示注入（用户输入和检索内容）；升级到人并交接上下文；评测（解决率、错误动作率、升级率、成本）；上线分阶段（辅助 → 低风险自动 → 扩大）。

### H4. 设计一个自主的编程智能体流水线（从工单到合并请求）
**骨架**：触发 → 创建沙箱（拉代码、无外网或白名单）→ 智能体循环（读代码、改、跑测试）→ 独立验证（测试、类型、安全扫描、可选的评审智能体）→ 开合并请求 → 人工评审。
**深入**：上下文管理（大仓库的检索与索引、子智能体）；预算与超时；凭证（只给最小权限的短期令牌）；防提示注入；失败与回退；指标（合并率、返工率、回归率、成本）；评测（用历史工单回放）。

### H5. 设计一个深度研究（deep research）智能体
**骨架**：规划者把问题拆成子问题 → 多个并行的研究子智能体各自搜索、阅读、摘要（隔离上下文）→ 汇总者综合并核对引用 → 产出报告。
**深入**：成本控制（并行度与 token 上限）；来源可信度与引用核验；去重与冲突证据；不可信网页内容的注入防护；终止条件；评测（事实准确率、覆盖度、引用正确率）；多智能体的 token 成倍增长要有预算。

### H6. 设计智能体的评测与回归流水线
**骨架**：数据集版本管理 → 可复现的运行器（固定配置、模拟环境）→ 评分器（规则、评审员、人工抽检）→ 报告与对比 → CI 门禁 → 线上采样评测与反馈回流。
**深入**：评审员校准与偏差；多次运行与显著性；环境状态检查；成本控制（分层评测）；红队与安全回归；提示词与模型版本的变更流程。

### H7. 生产事故：一个智能体在生产环境反复调用同一个工具，成本飙升，你怎么处理？
**止血**：触发熔断或停掉该租户或版本的运行，保护预算。**定位**：看 trace，找出开始重复的那一步，检查工具返回、终止条件、提示词与上下文；比较与正常运行的差异。**根因**：例如工具返回不可操作的错误、结果被截断导致模型认为失败、缺少"完成"判据、循环检测缺失。**修复**：工具返回更清晰的信息；步数与重复检测；预算熔断；把案例加入回归集；补充告警。**复盘**：为何监控没有更早发现。

### H8. 设计一个面向财富 500 强的多租户检索增强智能体平台
**骨架**：身份与单点登录；文档摄入（解析、切块、嵌入、打权限标签）；按租户隔离的索引；检索时硬过滤与文档级权限校验；工具调用使用代表用户的凭证；沙箱执行；按租户的缓存键、配额与预算；审计与追踪（脱敏、隔离存储）；数据驻留与删除流程。
**深入**：如何证明隔离（测试、渗透、审计）；如何处理跨租户的共享知识；密钥与加密；可观测性与合规报告；评测的租户级切片。

### H9. 怎样让一个智能体在服务升级时不丢失正在运行的任务？
运行状态外置；工作进程无状态、可滚动重启；长时间活动用心跳，被中断后由其他工作进程接手；版本固定（旧运行用旧逻辑）；数据库状态模式向后兼容；用优雅停机让工作进程完成或交还当前任务；灰度发布与回滚。

## I. 编码题清单

面试可能让你现场实现下列小模块（不一定允许使用 AI，以面试说明为准）。建议每个都能在 20 到 30 分钟内写出可运行版本，并口头说明边界情况。

1. **从零实现智能体循环**：模拟一个会返回工具调用的模型，实现解析、执行、追加结果、终止条件、步数和 token 预算。
2. **带指数退避和抖动的重试装饰器**：区分可重试与不可重试的错误，支持最大次数和总超时，尊重取消。
3. **幂等执行器**：给定幂等键，保证有副作用的函数只执行一次；处理"执行中"的并发请求；记录结果并支持崩溃后恢复。
4. **有界并发的并行工具调用**：用 `asyncio.TaskGroup` 加信号量，每个调用有超时，部分失败的处理，取消的传播。
5. **检查点与恢复**：把运行状态序列化到存储，模拟崩溃后从最后一个完成步骤恢复，确保不重复已完成的副作用。
6. **重复调用与循环检测**：对工具名加规范化参数做哈希，统计窗口内次数，超限时中断并给出提示。
7. **JSON 模式校验与修复循环**：校验模型输出，失败时把错误信息回传并重试，限制次数。
8. **令牌预算与速率限制**：实现按租户的令牌桶，同时限制请求数和 token 数。
9. **简易评测框架**：数据集 → 运行 → 评分（规则加模拟评审员）→ 汇总（通过率、置信区间）→ 与基线对比。
10. **有向无环图执行器**：带依赖的任务并行执行，失败传播与重试，输出执行轨迹。
11. **按租户隔离的语义缓存**：键包含租户与策略版本，带过期与容量限制（可用最近最少使用淘汰）。
12. **一个简单的状态机引擎**：定义状态与转移、守卫条件、超时、持久化与幂等转移。

### 一个贯穿全场的主线
资深智能体工程师的回答，反复回到这几句话：**把强制性规则放在代码和策略里而不是提示词里；每一步都可持久化、可恢复、可幂等；用评测而不是直觉做决策；默认最小权限与租户隔离；先简单后复杂，每增加一层复杂度都要有数据证明。**
